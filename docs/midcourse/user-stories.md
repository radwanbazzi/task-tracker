# Task Tracker — Due Dates & Comments: User Stories (Final)

Extends the Modules 1–3 Task Tracker (FastAPI \+ Pydantic v2 backend, vanilla-JS Kanban frontend) with due dates \+ an overdue filter, and task comments. This version incorporates a senior-dev testability review and a full edge-case pass on top of the earlier product-owner decisions.

## User Stories

| ID | Feature | Story | Acceptance Criteria | Failure Cases | Assumptions I Made |
| :---- | :---- | :---- | :---- | :---- | :---- |
| A1 | Due dates & overdue filter | As a team member, I want to set a due date when I create a task so that I know when it needs to be finished. | 1\. Creating a task with a valid `due_date` (e.g. "2026-08-01") returns 201 with a task whose `due_date` matches exactly what was submitted. 2\. Creating a task without a `due_date` succeeds (201) with `due_date` null and `is_overdue` false. 3\. Sending `due_date` as an empty string ("") is treated the same as omitting it — the task is still created (201) with `due_date` null, matching how the app already treats an empty `assignee` as null. 4\. Creating a task with `due_date` set to a date before today (e.g. today minus 5 days, computed relative to the test's run date) is allowed and returns 201; the created task's `is_overdue` is true immediately, with no update required. 5\. In the UI, the create/edit modal has an optional due date input — a task can still be created without filling it in. | 1\. `due_date` in an invalid format (e.g. "21-07-2026", "08/01/2026") or an unparseable value (e.g. "next Friday") → 422\. 2\. `due_date` as an invalid calendar date (e.g. "2026-02-30") → 422\. | Empty string and omitted `due_date` are handled identically, matching the app's existing `assignee`\-to-null behavior. |
| A2 | Due dates & overdue filter | As a team member, I want to see at a glance which tasks are overdue so that I can prioritize what's already late. | 1\. GET /tasks and GET /tasks/{id} both return 200 with `is_overdue` included on every task, computed by the backend. 2\. A task with `due_date` strictly before today (computed relative to the test's run date, e.g. today minus 1 day — never a fixed literal) and status ToDo or InProgress has `is_overdue` \= true. 3\. A task with `due_date` strictly before today (same relative construction) and status Done has `is_overdue` \= false. To set this up in a test, move the task ToDo → InProgress → Done — two PATCH calls — since ToDo → Done directly is an invalid transition and returns 422\. 4\. A task with `due_date` equal to today (computed as today's date at test time, not a fixed literal) and any non-Done status has `is_overdue` \= false — only a strictly earlier date counts as overdue. 5\. In the UI, every task card shows its due date (if set) and displays a visible "Overdue" pill whenever `is_overdue` is true. | 1\. A POST or PATCH body that includes `is_overdue` directly → 422 (rejected as an unrecognized field, same as any other `extra="forbid"` violation). 2\. GET /tasks/{id} for an id that doesn't exist → 404\. | "Today" is the backend server's own system-clock date, with no timezone conversion. `is_overdue` is computed fresh on every read, not cached. |
| A3 | Due dates & overdue filter | As a team member, I want to change a task's due date after creating it so that I can adjust my plan when priorities shift. | 1\. PATCH /tasks/{id} with a new valid `due_date` returns 200 with the task's `due_date` updated. 2\. If the change flips whether the task is overdue (e.g. moving `due_date` to on/after today, computed relative to the test's run date, not a fixed literal), the returned `is_overdue` reflects the new state immediately. 3\. In the UI, editing the due date in the modal and saving updates the date on the card and adds/removes the Overdue pill accordingly. | 1\. PATCH with an invalid `due_date` format (e.g. "2026/08/01") → 422\. 2\. PATCH on a task id that doesn't exist → 404\. | Same `due_date` format/validation rules apply on PATCH as on create (see A1). |
| A4 | Due dates & overdue filter | As a team member, I want to filter the task list down to only overdue tasks so that I can focus on what's late first. | 1\. GET /tasks?overdue=true returns 200 with only tasks where `is_overdue` is true. 2\. GET /tasks?overdue=true\&status=InProgress returns 200 with only tasks that are both overdue and InProgress — filters combine with AND, not OR. 3\. GET /tasks?overdue=true\&priority=High returns 200 with only tasks that are both overdue and High priority — the same AND-combining rule applies to priority as to status. 4\. In the UI, an overdue filter control sits alongside the New Task button; enabling it re-renders the board to only overdue tasks. | 1\. GET /tasks?overdue=true\&status=Done → 200 with an empty list `[]`, since a Done task can never be overdue by definition. 2\. GET /tasks?overdue=notabool → 422\. | `overdue` is a strict boolean query param (true/false); other truthy strings like "1" or "yes" are not assumed accepted. |
| A5 | Due dates & overdue filter | As a team member, I want to clear a task's due date so that I can remove a deadline that no longer applies. | 1\. PATCH /tasks/{id} with `due_date` set to null (or an empty string, treated the same) returns 200 with `due_date` cleared. 2\. After clearing, `is_overdue` becomes false regardless of status, since there's no due date to compare against. 3\. In the UI, clearing the due date in the edit modal and saving removes the date and any Overdue pill from the card. | 1\. PATCH on a task id that doesn't exist while attempting to clear it → 404\. 2\. Sending an invalid type for `due_date` (e.g. `false` or `0`) instead of null, "", or a valid date string → 422\. | Clearing requires the `due_date` key to be present in the PATCH body (as null or ""); omitting the key entirely leaves the existing value unchanged (same `exclude_unset` partial-update pattern used elsewhere in the app). |
| B1 | Task comments | As a team member, I want to add a comment to a task so that I can share updates or notes with the rest of the team. | 1\. POST /tasks/{task\_id}/comments with non-blank text returns 201 with the created comment: id, task\_id, text, author, created\_at. `author` is optional and may be absent from the request. 2\. Comment text is trimmed of leading/trailing whitespace before being stored. 3\. If `author` is omitted, null, or whitespace-only after trimming, it is stored as null — a blank author is never rejected, unlike text. 4\. In the UI, the comment form requires a message before it can be submitted; the author field is optional and can be left blank. | 1\. Blank or whitespace-only `text` (after trimming) → 422 with detail message "Comment text is required and cannot be blank". 2\. `text` over 1000 characters, or `author` over 50 characters → 422\. 3\. POST to a `task_id` that doesn't exist → 404\. | `author` reverted to optional this round (was mandatory previously) — flag if that switch wasn't intentional. Keeping the existing 50-character cap on author since this round's rules didn't say to drop it. `id`, `task_id`, and `created_at` remain server-assigned. |
| B2 | Task comments | As a team member, I want to see all comments on a task, with who wrote them and when, so that I can follow the discussion before making changes. | 1\. GET /tasks/{task\_id}/comments returns 200 with every comment for that task, each including text, author, and created\_at. 2\. Comments belonging to other tasks are never included in this task's list. 3\. In the UI, the edit modal's comments section displays each comment's text, author (if present), and posted time. 4\. In the UI, a comment with a null author displays a neutral placeholder such as "Anonymous" rather than blank space or the literal word "null". | 1\. GET /tasks/{task\_id}/comments for a `task_id` that doesn't exist → 404\. | ASSUMPTION: the rules specify null is stored but not how the UI renders it — assuming a placeholder label, matching how this worked before the author-required detour. |
| B3 | Task comments | As a team member, I want the comment count and list to update immediately after I add or delete a comment so that the task card and modal always reflect the current discussion. | 1\. After a successful POST /tasks/{task\_id}/comments, a follow-up GET /tasks/{task\_id}/comments includes the new comment (one more entry than before). 2\. In the UI, after successfully adding a comment, the task card's comment count increases by one with no page reload. 3\. In the UI, after successfully deleting a comment, the count decreases by one and the comment disappears from the modal's list with no page reload. 4\. In the UI, the comment count shown on a task card matches the number of comments listed inside that task's edit modal when it's opened. | 1\. In the UI, if adding a comment fails validation, the comment list and displayed count in the modal stay exactly as they were before the attempt. 2\. In the UI, if deleting a comment fails, the comment list and displayed count in the modal stay exactly as they were before the attempt. | Every criterion here is now single-mechanism testable: AC1 is a backend-only pytest check; the rest are frontend-only manual checks. The backend half of "delete removes it" is already covered by B5's AC1, so it isn't duplicated here. |
| B4 | Task comments | As a team member, I want a task's comment list to show only that task's comments in a consistent order so that I can follow the conversation without noise from other tasks. | 1\. GET /tasks/{task\_id}/comments returns 200 with only comments whose `task_id` matches the requested task. 2\. Comments are returned ordered oldest-first by `created_at`, so the thread reads in the order it happened. 3\. The endpoint returns the full comment list with no pagination, truncation, or limit applied. | 1\. A task that exists but has no comments yet → 200 with an empty list `[]`. | Oldest-first order was confirmed as the intended read order for a discussion thread. |
| B5 | Task comments | As a team member, I want to delete a comment, and have a task's comments cleaned up automatically if the task itself is deleted, so that the discussion stays accurate and tidy. | 1\. DELETE /tasks/{task\_id}/comments/{comment\_id} returns 204 with no body; a following GET no longer includes it. 2\. Deleting a task (existing DELETE /tasks/{id}, 204\) also removes all of that task's comments from storage (verified in tests via direct storage inspection, since the comments endpoint 404s once the parent task no longer exists). 3\. In the UI, clicking delete on a comment in the modal removes it from the visible list immediately. | 1\. DELETE .../comments/{comment\_id} where the comment doesn't exist (or doesn't belong to that task) → 404\. 2\. DELETE .../comments/{comment\_id} where the `task_id` itself doesn't exist → 404\. | Cascade delete happens synchronously inside the same DELETE /tasks/{id} call — no separate or async cleanup step, consistent with in-memory storage. |

## Alternatives considered and excluded

**Feature A — Due dates & overdue filter**

- Computing `is_overdue` on the frontend instead of the backend — excluded because the design explicitly requires backend computation, and client-side dates would drift across timezones or incorrect system clocks between team members.  
- Adding an optional time-of-day to `due_date`, with timezone-aware overdue calculation — excluded because it directly contradicts the original scope and because there's no user-account system to anchor "whose timezone" the time would be interpreted in.  
- Recomputing `is_overdue` via a background job instead of live on read — excluded because there's no scheduler in this stack, and it would only add staleness versus computing it live.

**Feature B — Task comments**

- Allowing comments to be edited after posting — excluded explicitly by the out-of-scope list; only create/read/delete are in scope.  
- Supporting threaded replies or @mentions — excluded explicitly by the out-of-scope list; comments stay flat and don't reference other users.  
- Paginating the comments list — excluded explicitly by the out-of-scope list; the full list per task is simple and sufficient here.
