# Reflection

> **Draft in my voice, based on things that actually happened during this project.** Every incident below is real and traceable to a commit or a terminal output in `verification.md` and `prompt-log.md`. I have reviewed it and edited it to reflect my own experience — I am not submitting anything I could not defend if asked about it.

I used two AI tools with a deliberate split. Claude acted as the planner and reviewer: writing user stories, drafting the mini-ADR, engineering the prompts I would run, and reviewing diffs and test output afterwards. VS Code's agent mode was the implementer, working directly on files in the repository. Keeping those roles separate mattered more than I expected. The planner never wrote production code, and the implementer never got to decide scope. When the implementer tried to widen a change, I had a written decision to point back to instead of an opinion.

The clearest moment AI helped was the design of the overdue rule. My instinct was to write a function that checked whether a due date was before today, with the function reading the clock itself. Claude pushed for `compute_is_overdue(due_date, status, today)` — passing the current date in as a parameter. That one decision meant every date-dependent test could compute its dates relative to `date.today()` at run time, so the suite has no hardcoded dates and will still pass next year without any clock-mocking library. Twenty-six tests depend on that choice, and I would not have made it on my own.

The clearest moment AI slowed me down was the first draft of my mini-ADR. It described SQLite, SQLAlchemy or SQLModel, foreign keys, request-scoped database sessions, transactions, and cascade deletes — an entire persistence layer my project does not have. My `storage.py` is a module-level Python dictionary. Had I handed that document to the agent, it would have installed an ORM and rewritten my storage layer, turning a scoped feature project into a migration project and breaking nineteen passing tests. I lost the better part of an hour rewriting the ADR against the code that actually exists.

The place where my review changed the result was smaller but more useful. My plan for the overdue filter was to fetch all tasks and filter the array in JavaScript. Reviewing it against my own ADR, I saw that would leave the `?overdue=true` endpoint I had just built and tested completely unexercised by the UI — the feature would look finished while half of it was dead code. I changed `fetchTasks()` to send the query parameter instead, and added a DevTools Network capture to `verification.md` as proof the filter runs on the server.

The theme across all three is the same. AI was fastest when I gave it a narrow, well-constrained job, and most dangerous when it filled a gap I had left unspecified. It never said "I don't know what your storage layer is" — it guessed, confidently and in detail. Checking the output against the actual code was the only thing that caught it.
